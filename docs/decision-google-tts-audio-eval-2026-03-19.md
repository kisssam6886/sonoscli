# Google TTS 真机听感评估结论（2026-03-19）

## 背景

在确认 Google Cloud Text-to-Speech API 已可调用之后，针对 Sonos 客厅设备做了一轮真实播报听感测试，目标是判断 Google 是否值得作为仓库内置 `say` provider 的优先路线。

## 测试方式

- 使用已验证可用的 Google TTS API key
- 真实调用 `text:synthesize`
- 生成普通话、粤语两组音频
- 通过本机临时 HTTP 向 Sonos 客厅设备发起播放
- 使用仓库内编译版 `./sonos`

测试音色如下：

- 粤语标准女声：`yue-HK-Standard-A`
- 粤语高清女声：`yue-HK-Chirp3-HD-Aoede`
- 普通话标准女声：`cmn-CN-Standard-A`
- 普通话高清女声：`cmn-CN-Chirp3-HD-Aoede`

## 真机结果

- 四段样本均成功在客厅 Sonos 上播放
- API 层面、音频生成层面、Sonos 播放链路层面均已验证打通
- 但用户主观听感反馈为：
  - “全部都不理想”
  - “和本地生成的差别不大”

## 结论

Google TTS 目前可视为：

- `技术可用`
- 但 `产品体验暂未达标`

也就是说，它已经证明“可以接”，但尚未证明“值得优先接进主流程”。

对于当前仓库阶段，更重要的不是再花时间把 Google provider 迅速合并，而是先守住下面这个判断：

- 如果 Google 的普通话 / 粤语自然度听起来与本地 macOS `say` 差距不明显，那么它目前不具备足够的产品优势来覆盖：
  - 接口接入成本
  - key / billing / quota 维护成本
  - 多 provider 支持复杂度

## 产品判断

当前不建议把 Google 作为默认 TTS 主路线，原因有三：

### 1. 听感提升不明显

这轮最关键的不是 API 能不能通，而是用户是否明显感到“更像真人”。  
当前答案是否定的。

### 2. 维护成本会抬高

一旦正式接入 Google provider，仓库后续就要维护：

- key 管理
- provider 参数映射
- voice 默认值
- 计费 / 限额说明
- 失败回退策略

如果声音收益不够明显，这些成本暂时不值。

### 3. 商业化方向要优先押“体验拉开差距”的能力

仓库如果要往商业化走，TTS 不只是“能播”，而是要做到：

- 更自然
- 更稳定
- 更像服务能力，而不是 demo 功能

Google 当前至少在这轮测试里，还没达到这个门槛。

## 对仓库的建议落点

现阶段建议：

1. 保留 Google TTS 验证结果，但不急着并入默认 provider
2. `say` 主路径继续以本地稳定方案为基线
3. 如后续继续做高自然度 TTS，对象优先级应重新排序：
   - 首先考虑有明确情绪 / 角色控制能力的 provider
   - 其次再看成本和接入复杂度

## 建议的工程策略

短期内建议采用：

- 默认播报：
  - 继续走本地稳定版
- Provider 架构：
  - 可以保留可扩展设计
  - 但不要为了“支持更多 provider”而优先合并一个听感不达标的实现

## 后续方向

如果继续推进 TTS，建议下一轮关注点不是“再试更多 Google voice”，而是：

1. 是否存在明显更自然的 provider
2. 是否支持粤语 / 普通话情绪化表达
3. 是否值得为商业化场景承担额外成本

## 本次决策摘要

一句话：

Google TTS 已验证“能用”，但暂未验证“值得用作主路线”，当前不建议把它作为仓库默认语音方案推进。
